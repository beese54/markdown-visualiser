# Security

> Security architecture, trust boundaries and who is responsible for what.

## Trust Boundaries

1. **Dropped files → browser pipeline.** Markdown and any embedded HTML are untrusted. The boundary is `rehype-sanitize` in `src/pipeline/render.ts`, placed directly after `rehype-raw`. Everything after it is generated by the application from a clean tree. See [ADR-002](adr/002-sanitiser-immediately-after-rehype-raw.md).
2. **Browser → `POST /api/export/pdf`.** The endpoint accepts whatever a caller posts, not only output from this client. It is treated as hostile HTML rendered in a real browser. [ADR-003](adr/003-contained-print-service.md)
3. **Network → container.** The service has no authentication, so exposure is controlled by port binding.

Content leaves the browser only at PDF export. It is held in memory for one request and never written to disk. The HTML export is local.

## Authentication

None, by design. The README and `docker-compose.yml` state that the app has nothing to authenticate. Anyone who can reach port 8080 can use the print service.

<!-- sources: docker-compose.yml, README.md -->

## Authorisation

None. There are no users, roles or protected resources.

<!-- sources: server/index.ts -->

## Secrets Management

No secrets exist in the repository, image or Compose file. Nothing is read from the environment except `PORT`, `HOST`, `STATIC_ROOT`, `LOG_LEVEL` and `NODE_ENV`.

<!-- sources: server/index.ts, Dockerfile, docker-compose.yml -->

## Session Handling

No sessions or cookies are set by the server. Each print request uses a fresh browser context, so no cookies, storage or service workers carry between documents.

<!-- sources: server/index.ts, server/pdf.ts -->

## API Security

Controls on the print endpoint:

| Control | Stops |
|---|---|
| `javaScriptEnabled: false` | script-driven fetch, exfiltration, infinite loops |
| Context-level default-deny routing (only `data:`, `blob:`, `about:` continue) | SSRF to internal hosts and cloud metadata, `file://` reads, CSS-only vectors (`@import`, `url()`, `<link>`) |
| Fresh `BrowserContext` per request, closed in `finally`; service workers blocked | state carrying between documents |
| `p-limit` (1–4) plus queue cap; 429 when saturated | unbounded browser spawning |
| `bodyLimit` 20 MB; 20 s `setContent`, 20 s default and 30 s overall deadlines | oversized bodies, documents that never settle |
| `title` HTML-escaped in the header template and truncated to 120 characters; download filename reduced to ASCII word characters | injection through title and headers |
| Generic 503 body, detail logged only | leaking paths and internals |

Response headers `x-content-type-options`, `referrer-policy` and `cross-origin-opener-policy` are set on every response. No `Content-Security-Policy` header is set by the server: uncertain — verify with developer whether one is intended.

The README and `tasks/todo.md` report these controls as verified by probe (`tests/e2e/adversarial.mjs`); this document has not re-run them.

<!-- sources: server/pdf.ts, server/index.ts, tasks/todo.md, README.md -->

## Network Exposure

Compose publishes `127.0.0.1:8080:8080` only. Binding to `0.0.0.0` would publish a headless browser that renders arbitrary posted HTML. The server itself sets `trustProxy: false`. The container runs as non-root `pwuser` (so the Chromium sandbox stays enabled), with a read-only root filesystem, all capabilities dropped and `no-new-privileges`. `ipc: host` is set because Chromium crashes without it, which slightly weakens isolation.

<!-- sources: docker-compose.yml, Dockerfile, server/index.ts -->

## Input Validation

- **Markdown/HTML:** the sanitiser schema strips `script`, `style`, `iframe`, `object`, `embed`, `link`, `meta`, `base` and `form`. Link `href` schemes are limited to `http`, `https`, `mailto`, `tel`, `irc`, `ircs`, `xmpp`. Image `src` is an explicit allowlist: `http(s)`, `blob:`, raster `data:image/*` (SVG excluded) and relative paths. Task-list `input` is pinned to disabled checkboxes. `id` and `name` are clobbered with the `user-content-` prefix by the sanitiser. Headings get unprefixed ids afterwards, downstream.
- **Server body:** `html` must be a non-empty string. `format` accepts `Letter`, otherwise `A4`. `title` must be a string. `landscape` is honoured only when exactly `true`.
- **Ingest limits:** 2000 files, 200 MB total, 10 MB per markdown file.
- **KaTeX** renders errors inline and does not throw.

<!-- sources: src/pipeline/sanitize.ts, src/pipeline/render.ts, server/index.ts, src/types/domain.ts -->

## Dependency Security

`package-lock.json` is committed and installs use `npm ci`. No automated vulnerability scanning or update bot is configured in the repository. `playwright-core` is pinned to the exact version of the base image. The rendering libraries define the sanitisation surface, so upgrade them with the pipeline tests and adversarial probe. See [DEPENDENCIES.md](DEPENDENCIES.md).

<!-- sources: package.json, Dockerfile, .github/workflows/docforge.yml -->

## Logging and Audit

The server logs through Fastify's logger. Failures are logged at `error`. There is no audit log, and no request bodies are logged by application code. Fastify's default request logging may record URLs: uncertain — verify with developer.

<!-- sources: server/index.ts -->

## Sensitive Data

User documents are the only sensitive data. They stay in the browser except for PDF export, when they are held in memory for one request. They may be disclosed only via the PDF response to the same caller. Nothing is persisted, and `/tmp` is the only writable path. Whether Chromium writes document content to `/tmp` during rendering: uncertain — verify with developer.

<!-- sources: README.md, server/pdf.ts, docker-compose.yml -->

## Rate Limiting

No per-client rate limit. The service uses a global concurrency limit and a queue cap (429 beyond `4 × concurrency` pending). One client can consume all capacity.

<!-- sources: server/pdf.ts -->

## Encryption and TLS

The server speaks plain HTTP. TLS termination is not provided in the repository, so a reverse proxy is required for any non-local deployment. No data is encrypted at rest, because none is stored.

<!-- sources: server/index.ts, docker-compose.yml -->

## Security Assumptions

- The service runs on loopback or a trusted network.
- The client inlines all assets before posting, so blocking all network access in the print browser costs nothing.
- The print browser has JavaScript disabled, so the HTML has no need to execute.
- `src/pipeline/sanitize.ts` exports a `printSchema` described as a server-side second filter. **It is not used anywhere**, and the server does not sanitise posted HTML. The controls above are the only protection.
- Mermaid is described as running in `securityLevel: 'strict'` (`tasks/todo.md`). The component was not read to confirm this.

<!-- sources: src/pipeline/sanitize.ts, server/pdf.ts, src/export/standalone.ts, tasks/todo.md -->

## Responsibilities

- **Developers:** keep the sanitiser before the generators and add tests for hostile payloads. Keep the print-service controls layered. Re-run `npm run test:security` after changes.
- **Operators:** keep port 8080 off untrusted networks, add TLS and access control in front of it if it is exposed, and keep resource limits.
- **Users:** decide whether to use PDF export for sensitive documents. The HTML export stays local.
